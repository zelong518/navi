# 性能测量与排障纪律

**方法**，与具体项目无关。每一条都对应一次真实的判断失误或一次有效发现——
规则的价值在于别人不用重犯。

具体环境的实测常数（存储/总线带宽上限、机器清单、已知坑）**不在本仓库**，
读 `$NAVI_HOME/cluster-facts.md`（不存在则参考同目录 `cluster-facts.example.md` 自建）。

## 一、测量纪律

### Rule 0：先测硬件上限，再谈优化

**没有上限就没有「够不够快」。** 一个吞吐数字是好是坏，取决于底层能给多少。
动代码之前先拿到天花板：存储/网络并发上限、总线带宽、以及问题规模装不装得进这台机器。

### 单次测量不可信

真实教训：早期记录的带宽上限是**单次测量**，多轮交错重测后数字明显不同。
**上限本身也必须用抗噪方法测。** 共享文件系统、多人共用的机器上尤其如此。

抗噪的做法是**交错 A/B**：不是「A 跑 3 轮再 B 跑 3 轮」，而是 ABABAB 取中位数。
顺序执行会把机器状态漂移（缓存、邻居负载、温度）算进被测差异。

### 微基准的排名不能外推到端到端

实测过两次：
- 某后端单进程微基准快 **1.3 倍**，多进程端到端**两者同速**
- 某参数在组件级基准上稳定复现 **+20%**，端到端 4 轮交错**两胜两负且方差更大**

> 两个口径的绝对值对不上时，**说明它们测的不是同一个系统**，
> 不要用一个去解释另一个。

### 多少差值才够行动

**约 6% 的中位差不足以行动**，尤其当方差同时变大。
把这种否定结论**写下来**，否则下一个人还要再花两小时重做同一件事。

### 冷热必须一致

实测：服务启动后头几分钟的时序**静默偏慢约 8.6%**，
而每个点内 3 次重复的极差只有 ±0.05%——**它看起来完全像可信数据**。

- 走出瞬态靠**累积工作量**，不是固定时长
- ⚠️ **「窗口平坦」不是充分判据**：新服务会在偏高处形成一个持续约 20 秒、
  平坦到 1% 内的**假平台**。正确判据是「平坦 **且** 相对上一窗口不再改善 **且** 熬够时间」
- ⚠️ 推论：**A/B 两个 arm 必须处在同样的热度上**，否则冷的那个会凭空慢一截，
  而这个差会被误读成被测特性的开销

### 在被测库之外定位根因

怀疑某个库的某条路径时，用**独立小程序**跑同样的系统调用/内核路径。
库内部的封装、线程模型、默认参数都会污染判断；独立复现能把「库的问题」
和「这台机器就这样」分开。

## 二、排障：Replay first

> **跑不起来的问题只会被争论，不会被修。**

### Step 1 — 先重建那次运行，别先读代码

每次运行都应留下 record（配置 + 代码快照 + 提交号）与日志。从 record 开始，不要从记忆开始。
**用不可变快照跑，不要用工作副本跑**——「但它现在好了」通常意味着有人改了工作副本。

没有 record 的运行是手工起的：**先补一个 record 再继续调**，
未记录的运行无法与任何东西比较。

### Step 2 — 先分类，再调查

按症状归类（启动/环境、守卫拒绝、服务不健康、输出不对、数字变了、早期 vs 稳态），
每类的第一个问题都不一样。**跳过分类直接读代码是最贵的路径。**

典型陷阱：**数字在前几十步好、后面坏（或反之）** → 那是启动开销
（编译、图捕获、缓存预热）与稳态的区别，不是 bug。

### Step 3 — 按成本递增收缩

每一步都比下一步便宜，所以严格按顺序：

1. **CPU 上的等价性测试**（秒级）——分开「模型/算法错了」和「引擎/系统错了」
2. **最小规模**：单卡、极小样本量
3. **参考实现 vs 快路径**跑同一输入——这就是参考路径要保持可运行的全部理由
4. **只有到这一步**才读 kernel / 引擎内部

### Step 4 — 收尾必须留下两个产物

一是**失败→通过的回归测试**，二是**结论记录**（改变了认知就写进实验 ledger，
没修就开 issue）。**两个都没有的修复会被重新发现。**

## 三、证据强度

| 结论 | 弱证据 | 强证据 |
|------|--------|--------|
| 「换了并行方式/实现，精度不变」 | benchmark 分数接近 | **预测逐字相同**（跨机逐比特一致） |
| 「两台机器等价」 | 都能跑起来 | 热态时序吻合到千分之几 + 全样本预测逐字相同 |
| 「这个优化有效」 | 一次测量变快了 | 交错多轮中位数 + 其他路径无回归 |
| 「改动没破坏别的」 | 目标用例通过 | 显式跑了其他路径的对照 |

分数是**聚合后的**指标，能掩盖互相抵消的错误。逐字/逐比特一致才排除了「碰巧总分相同」。

## 四、不要比较不可比的东西

- **加载耗时不能用来横向比存储后端**：同一份数据第二次加载走的是 page cache，
  实测能快一个数量级——那时测的是内存带宽，不是存储
- **配置不同的两次运行不要手算差值**。工具因为「受控配置不同」拒绝算 delta 时，
  不要绕过它自己算
- **buffered 与 O_DIRECT 不是同一件事**：冷读时 buffered 可能慢数倍

## 五、编排要求

1. 用户问「这个数字对不对 / 要不要调这个参数」时，**先查是否已有否定结论**
   （`$NAVI_HOME/cluster-facts.md` 的「已否掉的方向」），别重做已经做过的实验。
2. 给性能建议前先确认**上限已知**；未知就先测上限。
3. 报告性能结论时必须带**测量条件**（机器、并发、数据量、轮数、冷热状态）与**中位数**，
   不要只报单次最好值。
4. 机器选择与各机器已知坑走 `/navi-server list`（清单在本地配置里，不入仓库）。
